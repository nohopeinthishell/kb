# Архитектура

Этот файл отвечает на один вопрос: **куда положить код, который я собираюсь написать.**

Читать целиком не обязательно. Если вы пришли за конкретикой — раздел 3 (куда что класть)
и раздел 6 (как добавить страницу).

---

## 1. Что уже есть в шаблоне

Проект собран из шаблона курса. Структура клиента плоская:

```
packages/client/src/
  pages/          экраны — по одному файлу на роут
  components/     переиспользуемые компоненты
  slices/         Redux-слайсы
  hooks/          хуки
  assets/         картинки, шрифты
  store.ts        сборка стора
  routes.tsx      таблица роутов
  constants.tsx   адреса серверов
  main.tsx        точка входа в браузере
  entry-server.tsx точка входа при серверном рендере
```

Помимо этого в `packages/client/server/` лежит небольшой Express-сервер — он рендерит
страницы на сервере. Это **не** наш бэкенд (наш — `packages/server/`), но правки в нём
иногда нужны: что именно и почему — в разделе 5.

Из библиотек уже подключены: React 18, Redux Toolkit, React Router 6,
styled-components, react-helmet-async. Тесты на Jest.

## 2. Как работает SSR, и почему это важно знать

Страница рендерится **дважды**: сначала на сервере в HTML, потом «оживает» в браузере.
Из этого следуют почти все правила ниже.

Практическое следствие номер один: **страница не может просто сходить за данными
в `useEffect`**, иначе на сервере отрендерится пустой экран. Поэтому в шаблоне каждая
страница экспортирует две вещи:

```tsx
// компонент
export const MainPage = () => { … }

// функция загрузки данных — вызывается и на сервере, и на клиенте
export const initMainPage = async ({ dispatch, state }: PageInitArgs) => {
  if (!selectUser(state)) {
    return dispatch(fetchUserThunk())
  }
}
```

Обе регистрируются в `routes.tsx`:

```tsx
{ path: '/', Component: MainPage, fetchData: initMainPage }
```

На сервере `fetchData` вызывается до рендера, данные попадают в стор, стор сериализуется
в HTML. В браузере стор поднимается уже заполненным, а хук `usePage` понимает, что данные
уже есть, и не грузит их повторно.

**Если не следовать этому шаблону — страница будет работать, но SSR для неё сломается.**

## 3. Куда класть новый код

| Пишу… | Кладу в… |
|---|---|
| Новый экран под роут | `pages/` + запись в `routes.tsx` |
| Кнопку, инпут, модалку — что-то без знания о домене | `components/` |
| Компонент форума или профиля | `modules/{название}/ui/` |
| Компонент вокруг игрового холста — шапка, карточка события, лог | `game/ui/` |
| Redux-слайс | `slices/` |
| Запрос к API | `api/` |
| Хук общего назначения | `hooks/` |
| Правило игры, формулу, расчёт | `game/core/` |
| Отрисовку на canvas | `game/render/` |
| Свою очередь, стек, сортировку | `lib/` |

Четыре папки, которых в шаблоне нет, — `modules/`, `game/`, `api/`, `lib/` — заводим сами.

### Почему `modules/`

Шаблонная плоская структура нормальна, пока файлов десяток. У нас будет форум, профиль,
игра и лидерборд — это сотня файлов, и в плоском `components/` они перемешаются.

`modules/` — это то же самое, что на бэкенде называют «модуль по фиче»: всё, что относится
к форуму, лежит в одной папке, а не размазано по трём.

```
modules/forum/
  ui/          компоненты форума
  api/         запросы к своему бэкенду
  model/       вспомогательная логика, если нужна
  index.ts     что видно снаружи
```

Правило: **импортировать можно только через `index.ts`**. Написать
`import { TopicRow } from 'modules/forum/ui/TopicRow'` нельзя, потому что тогда через месяц
любой файл будет зависеть от любого, и модуль перестанет быть модулем.

Redux-слайсы при этом остаются в `slices/` — так уже устроен `store.ts` в шаблоне,
и ломать это ради красоты не стоит.

## 4. Три слоя игры

Игра — единственное место, где мы отступаем от «как проще» ради «как правильно».
Причина в том, что это самая сложная часть проекта, и её нужно уметь тестировать
и показывать на защите.

```
game/
  core/     правила игры
  render/   отрисовка на canvas
  ui/       React-компоненты вокруг холста
```

**`core/` — правила.** Чистый TypeScript. Не импортирует React, Redux, canvas, fetch.
Не знает даже, что существует браузер.

Смысл в том, что правила можно прогнать в тестах без запуска приложения: подсунул состояние,
получил новое, сравнил. Партию из шести недель тест проходит за миллисекунды.

Наружу торчат три функции, и больше ничего:

```ts
// переход недели: событие, гости, доход, репутация, износ
function tick(state: GameState, choice: ChoiceId | null): GameState

type GameAction =
  | { type: 'repairTable' }
  | { type: 'hireHelper' }
  | { type: 'buyProvision' }

// действие игрока внутри недели: ремонт стола, помощник, провизия
function applyAction(state: GameState, action: GameAction): GameState

// прогноз для кнопки «Следующая неделя»: «доход ~380, расходы ~290»
function forecast(state: GameState): { income: number; expenses: number }
```

Все три чистые: одинаковый вход всегда даёт одинаковый выход. Случайность приходит снаружи
через сид, иначе тесты были бы недетерминированными.

`applyAction` нужен отдельно, потому что действия происходят **внутри** недели: игрок
чинит стол и сразу видит новый зал, не дожидаясь перехода. `forecast` — потому что прогноз
на кнопке считается по тем же формулам, что и `tick`. Если посчитать его в компоненте,
формула окажется в двух местах и разъедется на первой же правке баланса.

Ремонт запускается одной кнопкой без выбора цели на canvas. UI передаёт в `applyAction`
только действие `repairTable`. `core` сначала ищет сломанный стол, затем изношенный,
проверяет деньги и переводит найденный стол в исправное состояние. Если ремонтировать
нечего, `core` возвращает ошибку. Правило доступности ремонта не дублируется в React.

Аналогия для тех, кто пришёл с бэкенда: `core` — это доменный слой. Он не знает,
кто его вызвал: HTTP, очередь или тест.

**`render/` — отрисовка.** Основная функция:

```ts
function render(ctx: CanvasRenderingContext2D, state: GameState, theme: Theme): void
```

Получает состояние и рисует его на холсте. Правил игры не знает — не решает, сколько
гостей придёт, только рисует тех, кто уже есть в состоянии.

Canvas только отображает состояние таверны. Для ремонта ему не нужны обработчики клика
или hit-test: выбор повреждённого стола полностью выполняется в `core`.

Постоянного игрового цикла нет: перерисовываем, когда изменилось состояние.
`requestAnimationFrame` включается только на время анимации перехода недели.

**`ui/` — React.** Шапка с показателями, карточка события, панель действий, лог.
Обычные компоненты. Правил игры в них быть не должно.

Проверка на ревью простая: **если формула или правило оказались в `.tsx` — это ошибка.**

## 5. Правила и причины

### Не трогать `window`, `document`, `localStorage` на верхнем уровне модуля

```ts
// сломает SSR — на сервере window не существует
const width = window.innerWidth

// нормально
useEffect(() => {
  const width = window.innerWidth
}, [])
```

Модуль исполняется и на сервере тоже. Обращение вне `useEffect` уронит рендер.

### Canvas монтируется только на клиенте

Холста на сервере нет. Компонент с canvas должен рендериться после монтирования
или подгружаться лениво. Иначе SSR падает при первом же заходе на страницу игры.

### Тема живёт в объекте и в cookie

В шаблоне styled-components, поэтому тема — это обычный JS-объект с цветами,
раздаваемый через `ThemeProvider`:

```ts
export const darkTheme = {
  colors: { bg: '#1a1a18', text: '#e8e6e0', tableOk: '#8fae5a' }
}
```

Canvas берёт цвета из того же объекта — никакого дублирования палитры.

Выбранная тема хранится **в cookie**, а не в localStorage. Причина: сервер должен знать
тему в момент рендера. Если он её не знает, то отдаст светлую, а браузер тут же переключит
на тёмную — на каждой загрузке будет заметное мигание.

В базе тема тоже сохраняется — это требование курса (PostgreSQL + Sequelize).
Cookie нужна для скорости, база — для того, чтобы тема ехала за пользователем.

### SSR-сервер шаблона меняем отдельным PR

В `packages/client/server/index.ts` четыре вещи, которые надо поправить (задача 1.15):

- **В проде он падает в собственном `catch`**: там вызывается `vite.ssrFixStacktrace(e)`,
  а `vite` вне dev — `undefined`. Любая ошибка рендера превращается в пустой ответ, то есть
  в белый экран. Нужен статический 5xx-фолбэк прямо здесь: ErrorBoundary серверный рендер
  не спасает, `renderToString` границами ошибок не ловится.
- Несуществующий роут отдаётся со статусом 200, должен быть 404.
- CSP убьёт инлайновые стили styled-components и `APP_INITIAL_STATE` без `nonce`.
- Приватным страницам нужна cookie в контексте — см. ниже.

### Cookie на сервере надо прокинуть в страницу

`createContext` в `entry-server.utils.ts` кладёт в контекст одно поле — `token`. Cookie
сессии API курса называется иначе, и при разных доменах фронта и сервиса сервер её вообще
не увидит. Поэтому:

- прод и dev живут на одном origin (nginx в 1.14, dev-прокси в 1.10);
- `PageInitContext` расширяется под реальные cookie сервиса — задача 3.21;
- `initXxxPage` на сервере ходит в API с этими cookie, иначе приватная страница
  отрендерится как гостевая и мигнёт после гидратации.

### Своя сортировка живёт в прототипе — значит, импортируется дважды

Патч `Array.prototype` применяется только в том окружении, где импортирован. Точек входа
две: `main.tsx` и `entry-server.tsx`. Забыли вторую — лидерборд работает в браузере
и падает при серверном рендере. Плюс нужен `declare global` для типов и исключение
для `no-extend-native` в ESLint.

### Тема для неавторизованного

Тема пользователя лежит в БД по `user_id`, но у гостя его нет. Порядок разрешения:
cookie → тема из БД (если вошли) → светлая по умолчанию. И `Vary: Cookie` на HTML,
иначе nginx однажды отдаст всем страницу в чужой теме.

### Никаких хардкоженных цветов в компонентах

Только `theme.colors.something`. Иначе вторая тема разъедется, и искать причину
придётся по всему проекту.

### Строгий TypeScript, без `any`

Требование курса — 95% TypeScript. `any` в PR — повод вернуть на доработку.

### Свои структуры данных не заменяем

В `lib/` лежат собственные реализации сортировки, очереди и стека. Они не для красоты:

| Структура | Где работает |
|---|---|
| Своя сортировка (в прототипе) | лидерборд |
| Очередь | гости, ожидающие свободный стол |
| Стек | история недель в логе |

Заменить их на `Array.prototype.sort` или обычный массив нельзя — это отдельное
требование курса, по нему проверяют.

### События игры — это данные, а не код

Событие описывается объектом в JSON: заголовок, текст, веса, условия, варианты с эффектами.
Движок его интерпретирует. Добавить новое событие = дописать объект в файл,
ничего не меняя в логике.

## 6. Как добавить страницу

Пошагово, потому что из-за SSR это не совсем очевидно.

**1.** Создать `pages/ForumPage.tsx` и экспортировать компонент:

```tsx
export const ForumPage = () => {
  usePage({ initPage: initForumPage })
  return <div>…</div>
}
```

**2.** В том же файле экспортировать загрузчик данных:

```tsx
export const initForumPage = async ({ dispatch, state }: PageInitArgs) => {
  if (!selectTopics(state).length) {
    return dispatch(fetchTopicsThunk())
  }
}
```

**3.** Зарегистрировать в `routes.tsx`:

```tsx
{ path: '/forum', Component: ForumPage, fetchData: initForumPage }
```

**4.** Если нужен новый слайс — создать его в `slices/` и подключить в `store.ts`.

**5.** Проверить страницу при выключенном JS или в исходном коде страницы: контент
должен присутствовать в HTML. Если его нет — SSR для страницы не работает.

## 7. Как добавить фичу форума

Для примера, чтобы был образец.

```
modules/forum/
  ui/
    TopicList.tsx
    TopicRow.tsx
    CommentForm.tsx
  api/
    topics.ts
  index.ts        export { TopicList } from './ui/TopicList'
```

Страница `pages/ForumPage.tsx` импортирует только `modules/forum`, ничего изнутри.
Слайс лежит в `slices/forumSlice.ts`, запросы — в `modules/forum/api/`.

## 8. Соглашения по коду

- Компоненты `PascalCase`, хуки `useCamelCase`, имя файла совпадает с экспортом
- Один компонент — один файл
- В `components/` попадает только то, что не знает о домене: `Button` — да,
  `TopicRow` — нет
- Ошибки обрабатываются везде: белого экрана не должно быть ни в одном сценарии
- Стили через styled-components, цвета только из темы
