# Журнал решений

Каждое принятое решение — три строки: что решили, почему, когда.
Нужно, чтобы через два месяца не начинать обсуждение заново.

Новое решение дописывается **сверху**. Если решение отменяется — не удаляем,
а помечаем «Отменено» и добавляем новую запись со ссылкой.

---

## Формат

```
## YYYY-MM-DD — Короткое название

**Решение.** Что именно решили.
**Причина.** Почему так, какие были альтернативы.
**Последствия.** Что это накладывает на проект.
```

---

## 2026-XX-XX — Игра урезана до минимального объёма

**Решение.** 6 недель, 2 показателя (казна, репутация), 4 стола, 3 работника
без найма, 3 действия, 8 событий. Вырезаны: настроение персонала, чистота зала,
строительство зон, экран персонала, форма найма, сохранения.

**Причина.** Сумма P0-задач превышала ёмкость команды примерно на 20 дней.
Требования курса резать нельзя — по ним принимают проект. Игру оценивают
по факту наличия, а не по глубине.

**Последствия.** Возврат вырезанного возможен не раньше конца третьего спринта
и только при реальном запасе. Порядок возврата — в `game-plan.md`.

## 2026-XX-XX — Своя сессия проверяется через API курса

**Решение.** Свой бэкенд не хранит пользователей. На каждый приватный запрос он
пробрасывает cookie в эндпоинт «текущий пользователь» API курса и по ответу решает,
пускать ли.

**Причина.** Авторизация целиком в чужом сервисе, дублировать её у себя — лишние
11 дней работы и рассинхрон данных.

**Последствия.** Нужен dev-прокси, чтобы локально всё жило на одном origin.
Нужна аккуратность с CORS, `credentials: 'include'` и `SameSite` у cookie при
трёх разных доменах.

## 2026-XX-XX — Тема хранится в cookie

**Решение.** Тема — JS-объект с цветами, раздаётся через `ThemeProvider` styled-components
(так устроен шаблон). Выбор пользователя лежит в cookie, а не в LocalStorage,
и дублируется в БД. Canvas берёт цвета из того же объекта темы.

**Причина.** При SSR чтение темы из LocalStorage даёт мигание: сервер рендерит
светлую, клиент переключает на тёмную.

**Последствия.** Тема доступна на сервере. Палитра не дублируется между CSS и canvas.
LocalStorage остаётся для черновиков форм и последней партии.

## 2026-XX-XX — Чистый Canvas API без библиотек

**Решение.** Зал рисуется примитивами через Canvas 2D. Ни Pixi, ни Phaser.

**Причина.** Требование курса сформулировано как «Canvas API». Объектов на экране
мало (около 20), сложных эффектов нет — библиотека не нужна.

**Последствия.** Хит-тестинг пишем руками. Спрайтов нет, всё рисуется
прямоугольниками и кругами.

## 2026-XX-XX — Клиент на Vercel, сервер и БД в Yandex Cloud

**Решение.** Статика клиента деплоится на Vercel (`root directory` = `packages/client`),
сервер и PostgreSQL — в Yandex Cloud.

**Причина.** Vercel предлагается шаблоном курса и даёт автодеплой PR из коробки.
Yandex Cloud указан в программе курса и покрывает сервер и управляемую БД.

**Последствия.** Три разных домена — нужно внимательно с cookie и CORS.

---

## 2026-XX-XX — Стартуем с шаблона курса

**Решение.** Проект форкнут с `Yandex-Practicum/client-server-template-with-vite`.

**Причина.** Готовая монорепа, Vite, SSR, docker-compose с PostgreSQL,
линтеры и хуки. Собирать то же самое с нуля — потерянная неделя.

**Последствия.** Монорепа на Lerna, зависимости добавляются через
`yarn lerna add --scope`. SSR уже есть и накладывает ограничения на весь клиентский код.
